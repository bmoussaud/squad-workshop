**Status:** active
**Supersedes:** []
**What:** Issue #61 should model each generated artifact with an authenticated owner subject, require that subject on generation and artifact reads in secure mode, return indistinguishable 404 responses for missing/unauthorized artifacts, and continue serving artifacts through the FastAPI application instead of issuing direct Blob/SAS redirects.

### D-issue-61-auth-design: Authenticated per-user artifact access — architecture decision
**ID:** D-issue-61-auth-design
**Decided At:** 2026-07-29T10:22:00+02:00
**By:** Morpheus (Lead)
**Status:** active
**Supersedes:** []
**What:** The recommended approach for issue #61 is Option B — app-level session auth with Entra ID via Container Apps Easy Auth, an `owner_subject` column on artifacts, and server-side proxy streaming through the existing FastAPI artifact route. This combines platform-managed identity (Entra ID) with minimal application-code coupling, preserves the existing blob-private-endpoint architecture, requires no SAS URL generation, and keeps the blast radius to one new middleware + one domain field.
**Why:** The app has no user concept today. Easy Auth provides identity at the platform layer without a custom login flow; the app only needs to read the `X-Ms-Client-Principal-Id` header injected by the sidecar. Streaming through FastAPI (already implemented) allows the authorization check to be a single `if artifact.owner != authenticated_subject: 404` gate. SAS-based options leak storage URLs and require new ports; fully custom auth (OAuth2 code flow in Python) is high-effort and error-prone. The trade-off is a Container Apps platform dependency, but this project already depends on Container Apps for hosting.

### D-switch-issue-61-session-auth-tests: Issue #61 app-owned Entra OIDC session auth tests

### D-issue-61-auth-design-revised: Authenticated per-user artifact access — revised architecture per PO ruling
**ID:** D-issue-61-auth-design-revised
**Decided At:** 2026-07-29T11:01:00+02:00
**By:** Morpheus (Lead), ratifying Benoit Moussaud (Product Owner) ruling
**Status:** active
**Supersedes:** ["D-issue-61-auth-design"]
**What:** The architecture for issue #61 is: (1) Identity provider: Entra ID, single tenant. (2) Auth flow: in-app OIDC authorization-code flow with PKCE, owned entirely by the application — NOT Container Apps Easy Auth, NOT a platform sidecar. (3) Session: app-managed signed/encrypted cookie after the OIDC exchange; session signing key from Key Vault. (4) Anonymous usage: not allowed anywhere; fail-closed middleware rejects unauthenticated requests before they reach route handlers. (5) Pre-existing ownerless artifacts: auto-deleted via the existing 30-day blob lifecycle policy (`infra/web.bicep:113-120`). (6) Owner identifier: the Entra ID token `sub` claim (opaque per-app GUID). (7) Cache policy for artifact responses: open, pending PO decision — recommendation is `private, no-store`. (8) OIDC library: `authlib` (new dependency, not currently in pyproject.toml). (9) Local passwords and invite codes explicitly rejected by PO — no credential storage surface. (10) Per-PR redirect-URI problem remains open and carries real cost (see architecture notes).
**Why:** The PO explicitly chose in-app OIDC over Easy Auth and explicitly rejected local passwords and invite codes. Easy Auth was originally recommended for its platform-edge fail-closed property, but the PO accepts that the application itself must enforce fail-closed semantics and prefers the simpler operational model. The original decision conflated "app-level session auth" and "Easy Auth" as if they were one option — they are architecturally distinct. This revision corrects the record and fully specifies the credential source, session management, and OIDC security requirements. The "high-effort and error-prone" assessment of in-app OAuth2 is mitigated by using `authlib` (a maintained, audited OIDC relying-party library) rather than hand-rolling the flow, and by the reduced complexity of a single-tenant scenario with one static redirect URI in dev.
### D-issue-61-pr-env-option-b: Per-PR Entra app registrations for in-app OIDC
**ID:** D-issue-61-pr-env-option-b
**Decided At:** 2026-07-29T11:11:09+02:00
**By:** Tank
**Status:** active
**Supersedes:** []
**What:** Issue #61 PR environments use per-PR Entra app registrations for the Product Owner-selected in-app Entra ID authorization-code flow. This decision stands alongside D-issue-61-artifact-auth-platform-revised as the narrower PR-environment implementation choice. The deploy workflow creates a deterministic per-PR app registration and short-lived client secret before azd provision so Bicep can inject OIDC client settings and app session keys as Container App secrets; the app is initially created without the final callback because the Container App FQDN does not exist yet. After azd provision emits SERVICE_WEB_URI from the private Container App, the workflow patches the exact redirect URI https://<fqdn>/auth/callback on that PR app registration, updates any runtime redirect-uri env needed by the Container App, then runs azd deploy. Close-time teardown deletes the per-PR app registration; failed runs attempt best-effort cleanup in an always-run cleanup step, and cancelled/missed runs are handled by the daily janitor. The janitor cannot rely on Azure resource tags because Entra app registrations are directory objects, so it must query Microsoft Graph for app registrations owned by the PR environment automation identity with the approved deterministic display-name/notes marker, cross-check the PR number against open GitHub PRs and age/TTL, and fail loudly on Graph query errors rather than silently skipping. The existing GitHub OIDC identity for app squad-workshop-pr-envs may be extended only if it is granted the Microsoft Graph Application.ReadWrite.OwnedBy application permission and made owner of the PR app registrations it creates; otherwise use a separate federated CI identity dedicated to PR app-registration lifecycle. Application.ReadWrite.OwnedBy is sufficient for creating app registrations and managing credentials/redirect URIs/deleting applications the CI identity owns, but it does not grant tenant-wide control over unowned app registrations, does not grant admin consent for arbitrary API permissions, does not assign directory roles, and does not manage Azure resources. The PR app client secret is a stored secret: Graph returns it once from addPassword, the workflow must mask it, pass it as a secure deployment value, store it only as a Container App secret, and remove it by deleting the app registration or removing the password during cleanup. Anonymous live Foundry validation is incompatible with the chosen auth model; the current anonymous POST to /api/generations must be removed or replaced by a real OIDC-authenticated browser/user test, never by a production auth bypass. Session signing/encryption keys and the OIDC client secret should use Container App secrets with a current/previous two-key session ring, not Key Vault, for this deployment.
**Why:** App-owned Entra OIDC revives the redirect-URI and client-credential friction that Easy Auth also had, but it is the coherent option for PR environments because anonymous/local bypasses would contradict the no-anonymous-usage ruling and crash against the existing blob-only PR artifact-store configuration. Creating the app before provision and patching the redirect after SERVICE_WEB_URI resolves breaks the FQDN dependency cycle without granting broad tenant administration. Container App secrets are the right platform primitive here because the current infrastructure already uses Container Apps without Key Vault, the app identity does not need to read auth secrets, per-PR secrets are short-lived and app-scoped, and a two-key ring supports rotation without logging out every user mid-session; Key Vault would add extra resources, RBAC, networking, and managed-identity secret-read surface without solving a current requirement.

### D-issue-61-design-closed: Issue #61 design — cache policy, PR auth, and final simplifications
**ID:** D-issue-61-design-closed
**Decided At:** 2026-07-29T11:16:00+02:00
**By:** Morpheus (Lead), ratifying Benoit Moussaud (Product Owner) ruling
**Status:** active
**Supersedes:** ["D-issue-61-auth-design-revised"]
**What:** Closes the two items left open by D-issue-61-auth-design-revised. (1) Cache policy is decided: `Cache-Control: private, no-store` on artifact responses (replaces `private, max-age=3600` at `web.py:292`). (2) PR environments authenticate for real via per-PR Entra app registrations — each PR gets its own app registration with its own client secret, created at deploy time, deleted at teardown. This is required for blast-radius isolation: a shared registration would mean every ephemeral PR environment holds the same OIDC client secret as production, so compromising any PR env yields prod's client credential. Per-PR registrations scope the blast radius to one PR environment. Dev and prod each have their own static registrations. The PR deploy workflow lifecycle is: create a new app registration before provision (`az ad app create`), patch the exact `redirect_uri` after `SERVICE_WEB_URI` resolves (`az ad app update`), delete the registration at teardown (`az ad app delete`), and the janitor sweeps orphaned registrations via Microsoft Graph for PRs that closed without teardown. The deploy identity needs `Application.ReadWrite.OwnedBy` or equivalent directory-write permission. (3) Consequence: `FANTASY_CARD_AUTH_MODE` does not exist. There is no mode switch and no auth-bypass surface anywhere in the deployed codebase — Switch's requirement that no production auth-bypass hook is acceptable is satisfied by construction, not by a runtime guard. (4) Local development authenticates against a dedicated dev Entra app registration with `redirect_uri=http://localhost:8000/auth/callback` (HTTP, not HTTPS — Entra permits localhost HTTP for dev). No mode switch needed. (5) Session signing key: Tank is right — Container App secrets with a two-key verification ring are adequate for MVP. My earlier Key Vault position understated the cost: there is no Key Vault anywhere in `infra/` today, so adopting it means a new `Microsoft.KeyVault/vaults` resource, its RBAC model (`Key Vault Secrets User` for the app identity), networking consistent with the existing posture (the storage account disables public network access at `web.bicep:103-109`, so the Key Vault would need a private endpoint too), and granting the managed identity secret-read permission — the exact surface Tank wanted to avoid. The security merits (rotation audit trail, soft-delete recovery, versioned rotation) are real but disproportionate for an internal-tool MVP with a two-key ring that already supports seamless rotation. Key Vault is the right hardening step if this tool grows to multi-tenant or external-facing, but for now Container App secrets are adequate. Tank's two-key ring (verify with both active keys, sign with newest) is adopted as the rotation mechanism.
**Why:** The PO rejected anonymous PR environments and confirmed `no-store` caching. Per-PR app registrations are required rather than a shared registration because a shared OIDC client secret across prod and ephemeral PR environments contradicts the blast-radius principle that motivated the Key Vault argument — if the signing key deserves isolation, the client credential does too. Removing the auth-mode switch eliminates an entire class of misconfiguration and test surface. The local-dev Entra registration is a one-time setup cost. Container App secrets over Key Vault for MVP is an honest cost-benefit call: the real infrastructure cost of Key Vault (new resource, private endpoint, RBAC, identity secret-read surface) is not justified when the two-key ring already provides rotation capability and the tool is single-tenant internal.
